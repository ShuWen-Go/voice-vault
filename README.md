# 听藏 · voice-vault

> 把一段会议录音，变成一份能直接用的结构化纪要 —— 而且**转写在你自己的机器上完成**。

**一个链接**：`https://liancang.app.workbuddy.host/voice/`（云端为演示模式，需口令）
**本地完整版**：`npm start` → <http://localhost:3000>

---

## 一、它解决什么问题

会议录音的常规做法是「上传到云端 ASR」：按分钟计费，而且**录音要交给第三方**。
而会议内容，恰恰是企业最敏感的数据之一。

听藏换了个思路：**转写不出机器**。

| | 云端 ASR API | 听藏 |
|---|---|---|
| 计费 | 按分钟 | **¥0**（本地 CPU） |
| 录音去哪 | 上传给第三方 | **不出本机** |
| 需要联网 | 是 | 只有「结构化」那一步 |

---

## 二、怎么做的

```
录音 → 本地转写 → 静音闸门 → 确定性纠错 → 云端结构化 → 落档 → 可回看
        AI ①      规则防线      规则防线        AI ②       存储
```

**AI 只用在两个「规则做不了」的地方，且每一处都配一条防线。**

### ① 本地转写（faster-whisper）

CPU int8，模型 `small` / `medium` 可选。**实测档位对比**（22.5 分钟真实电话录音）：

| 指标 | small | medium |
|---|---|---|
| 转写耗时 | 445 s | 877 s |
| RTF | **0.33** | 0.65 |
| 输出标点 | 无 | **有** |

⇒ 结论：**档位取决于音频类型** —— 清晰音频 small 够用；真实会议 medium 更准且带标点。

> ⚠️ 最初的结论「换更大模型并不更准」是基于**一段讲解视频**得出的，后来被**真实录音推翻**。
> 教训：**单一样本推不出通用结论** —— 结论必须标注样本条件。

### ② 静音段幻觉闸门（纯规则，零成本）

起因是一次**实测翻车**：真实会议里有一段约 1 分半的**低电平环境噪声**（没人说话），
Whisper 的 VAD 把它当成人声，于是模型**凭空造句** ——
而且造出来的正是我自己写进 `initial_prompt` 的那句引导语，还重复了两遍。

对会议纪要来说这是**最坏的一类错误**：**编造的内容看起来跟真的一模一样**。

四层判据，全部确定性（无模型），从零风险排到低风险：

| 层 | 判据 | 实测依据 |
|---|---|---|
| ① **提示词回声** | 文本落在提示词 / 指令句式里 | 模型原文背出「请使用简体中文转写」 |
| ② **字幕套话** | 命中「谢谢观看」这类套话，且句子很短 | 最常见的另一类幻觉 |
| ③ **静音段** | 能量 `< 0.5 × p50` **且** `no_speech_prob > 0.6` | 静音段实测 RMS ≈ **0.43×p50**、概率 **0.67**；而真实语音段概率 ≤ **0.50** |
| ④ **连续重复** | 与上一段归一化后完全相同且很短 | 幻觉常成对出现 |

> **两个条件同时成立才丢** —— 单看能量会误伤轻声说话，单看语音概率会误伤远场回声。
> 能量基准用**相对值**（p50）而不是绝对分贝 ⇒ 换设备、换场地**不用重调阈值**。

与纠错层同一条纪律：**不覆盖原文**（只打标记）、**可重跑**（转写最贵，闸门免费）、**可审计**（丢了哪段、凭什么）。

### ③ 确定性纠错（纯规则，零成本）

语音转写的错字是**系统性高频重复**的：

| 转写结果 | 应为 | 出现次数 |
|---|---|---|
| 技术 / 技效 | **绩效** | 31 |
| 新测 | 薪资 | 6 |
| 年中奖 | 年终奖 | 2 |

⇒ **同一条规则修 31 处**，杠杆率 31:1。而实测**堆更大模型并不更准**。
所以：**确定性的东西交给规则，别交给模型。**

三条安全设计：

- **exact 规则** —— 「技效」本身不是词，直接换，零风险
- **contextual 规则** —— 「技术」只在邻近出现「个人 / 组织 / 年终」时才换。
  实测全文 7 处「技术」**只改 1 处**（那处实为「基数」），**保住 6 处真「技术」**
- **原文永不覆盖** —— `raw` 字段留着，每条改动带位置与依据，完全可审计

### ④ 云端结构化 + 三层判据

9 个字段（`meetingType` / `title` / `summary` / `keyPoints` / `numbers` / `decisions` / `todos` / `openQuestions` / `risks`），
**全字段带 `at` 时间戳** ⇒ 每条都能回指录音的第几分几秒。

判据分三层：

1. **结构层** —— 剥代码围栏 + `JSON.parse`
2. **字段层** —— schema 校验（必填、类型、条目上限）
3. **实体层** —— 时间戳必须命中输入时间轴；`owner` / `numbers` 必须在原文出现

⚠️ **归纳类内容（摘要、要点）核不了 —— 所以如实标注「AI 归纳，建议核对」，不假装确定。**

## 三、实测数据

| 指标 | 值 |
|---|---|
| 22.5 分钟录音 | 转写 **13.5 分钟**（RTF 0.60）→ 504 段 / 6233 字 |
| 纠错 | 修正 **37 处**，误伤 **0** |
| 结构化 | **14.1 秒** / 10883 tokens（≈ ¥0.02） |
| 时间戳核验 | **36 / 36 命中** |
| 数字编造 | **0** |

**云端演示用的那段公开语料**（AISHELL-4，38.3 分钟、8 通道远场、5 说话人）：

| 指标 | 值 |
|---|---|
| 转写 | **19.6 分钟**（RTF **0.512**，medium）→ **1042 段 / 6965 字** |
| 幻觉闸门 | 丢弃 **0 / 1042**（**真实语料上零误伤**；人造幻觉样本 3/3 全抓） |
| 纠错 | 0 处（词表面向薪酬场景，本段不适用 —— 如实为 0，不凑数） |
| 结构化 | **15.7 秒** / 14914 tokens → 8 要点 / 5 数字 / 1 决议 / 6 待办 / 5 风险 |
| 时间戳核验 | **25 / 25 命中** |
| 数字编造 | **0** |

> ⚠️ 一个诚实的差异：远场录音（34.8 dB 信噪比差、有混响）比电话录音**难很多** ——
> 同一段 38 分钟只转出 **6965 字**（该语料人工标注全文是 10214 字），即**召回约 68%**。
> 而且输出几乎没有标点（电话录音那一段是有的）。**这类"能力边界"应该写在产品里，而不是藏起来。**

## 四、演示语料：用了什么、以及它教了什么

云端演示用的那段录音是 **AISHELL-4**（AISHELL 开源中文会议语料，**Apache-2.0**）测试集的一场，
8 通道远场录音、**38.3 分钟**、5 位说话人、剧本式演练（一场「家长会」讨论）。

**为什么选它**：

| 要求 | 它的表现 |
|---|---|
| 真实会议（不是朗读） | ✅ 多说话人、有插话、有停顿、有远场混响 |
| 许可干净 | ✅ Apache-2.0，可直接随包分发 |
| **能公开** | ✅ **剧本演绎 + 说话人匿名**（只标 `001-M`）；我逐条扫过全文：**0 手机号 / 0 身份证 / 0 邮箱 / 0 金额 / 0 机构名** |

### 顺手做了一个「多通道选择」实验

8 通道阵列录音，最自然的做法是**直接混音**。实测**这是最差的做法**：

| 做法 | 平均置信度（两段独立窗口） |
|---|---|
| **混音（8 通道平均）** | **−0.355 / −0.281（两次都在最差一档）** |
| 单通道 ch4 | **−0.271 / −0.262（两次都最优）** |

原因是通道之间存在**到达时延差**，直接相加会产生干涉、把语音"抹糊"。

> ⚠️ 但第一版实验我只看**置信度**，结果 `ch0` 以 −0.219 排第一 ——
> 查下去才发现它**只转出了 5 段、内容严重不全**（只抓住开头几句简单的话）。
> ⇒ **置信度必须和「覆盖率」一起看**，否则会被"只挑容易的"骗到。

最终按「覆盖率相同则比置信度」选定 **ch4**，转成单声道 16 kHz（38 分钟压到 **13.5 MB**）。

### 它暴露的产品缺陷（见 §二·②）

正是这段语料的**静音段**，让「模型凭空背出提示词」这个缺陷第一次现形 ——
在此之前的语料（电话沟通、讲解视频）连续说话、没有空档，**永远撞不出来**。

## 五、已知取舍（不是漏了，是判断后砍的）

| 没做 | 为什么 |
|---|---|
| **说话人分离** | faster-whisper 不提供；pyannote 只给编号不给姓名，拿到 `speaker_0` 还得再猜一次。当前用「LLM 推断 + 明标推测」 |
| **云端真转写** | 沙箱没有 1.5GB 模型，长音频 CPU 推理也不合适 ⇒ 云端只做**演示模式**，界面如实标注 |
| **换档重转写** | 低频；且它会引入「纪要基于旧转写」的级联不一致 |
| **列表页批量操作** | 数据量只有个位数，是伪需求 |

## 六、跑起来

```bash
# 依赖 Python + faster-whisper（见 app/asr/requirements.txt）
npm start        # → http://localhost:3000
```

`.env` 关键项：

| 变量 | 说明 |
|---|---|
| `VV_PYTHON` | 跑 ASR 的 Python 解释器 |
| `VV_MODEL_DIR` | 本地模型根目录（下面按档位分 `small/` `medium/`） |
| `VV_DATA_DIR` | 数据目录。**建议指到项目外** —— 发布打的是整个磁盘目录，真实录音留在项目里会被一起传走 |
| `VV_ACCESS_TOKEN` | 访问口令（留空 = 不启用，本地免登录） |

## 七、四条最值钱的教训

1. **防线本身也要被验证。**
   第一版实体核验器把 **9 个完全正确的输出误报成「编造」**（模型把口语「三个月」标准化成「3个月」）。
   **核验器自己错了，比没有核验器更糟** —— 没有防线时用户知道要自己核对；防线误报，用户会以为系统在骗他。

2. **同一类坑会换个形态再来一次。**
   给数字核验加「数字边界」后，又把「3千」（归一化成了 `3000`）判成可疑。
   ⇒ **凡是「更严格」的核验改动，都必须拿真实样本回归一遍。**

3. **本地过 ≠ 云端过。**
   访问控制用 HTTP Basic，本地全对、上云一律 `401` —— 查响应头才发现：**网关把 `Authorization` 头剥掉了**，
   401 还是自己服务发的。连「错在哪一层」都要靠响应头反推。

4. **"更严格"不等于"更对"。**
   给数字核验加「数字边界」后，`value:"3"` vs 原文「3千」被误判成可疑（归一化把「3千」拼成了 `3000`）。
   核验器**误报**比漏报更糟：漏报用户会自己核对，误报会让用户**以为系统在骗他**。
   ⇒ 凡「更严格」的改动，必须拿真实样本回归。

---

## 八、已知不足之处

- **纠错词表偏领域** —— 当前词表来自「薪酬沟通」语料。它做的是**机制**（能修 / 防误伤 / 可审计 / 可迭代），
  不是万能词表。真实产品里它靠**用户反馈 + 领域积累**长出来。
- **单通道演示音频** —— 演示用的是 8 通道里的一路。真做产品应当做**波束成形 / 通道择优**，而不是固定单路。
- **不做说话人分离** —— 见 §五。AISHELL-4 自带 rttm 标注，正好留作 V2 做 diarization 的评测基准。

## 九、目录结构

```
app/
  server.mjs          零依赖 Node http 服务（静态托管 + API）
  transcribe.mjs      转写编排：子进程 / 队列 / 进度 / 取消 / 幂等
  gate.mjs            静音段幻觉闸门（四层确定性判据，幂等、可重跑）
  gate-rules.json     闸门规则（改完即时生效，不用重启）
  correct.mjs         纠错引擎（exact + contextual，幂等、可重跑）
  corrections.json    领域纠错词表
  structure.mjs       结构化：强约束 prompt + 三层判据 + 实体核验
  store.mjs           聚合层：三层产物 → 一条记录
  export.mjs          Markdown 导出（区块顺序随会议类型变）
  index.html          单页三视图（列表 / 处理中 / 详情）
  asr/
    transcribe.py     Whisper 推理（stdout JSON 行协议 + 流式进度 + 判据落盘）
    requirements.txt  依赖锁（av==18.0.0 是实测踩坑换来的）
    fetch_model.py    模型下载（走 hf-mirror）
tools/
  pick_channel.py    多通道选择实验（用「覆盖率 + 模型置信度」双指标挑最优通道）
  make_demo_audio.py 把公开语料的多通道录音压成单声道演示音频
```

### 复现演示音频

```bash
# 1) 取公开语料（AISHELL-4 测试集某一场，Apache-2.0）
curl -L -o aishell4.flac \
  "https://hf-mirror.com/datasets/AISHELL/AISHELL-4/resolve/main/test/wav/S_R004S04C01.flac"

# 2) 多通道择优（3 个时间点 × 8 通道 + 混音，双指标）
python tools/pick_channel.py aishell4.flac <模型目录> ./probe 60,900,1800 20

# 3) 按选出的通道压成单声道 16k（38 分钟 → 约 13.5 MB）
python tools/make_demo_audio.py aishell4.flac demo.m4a ch4
```
